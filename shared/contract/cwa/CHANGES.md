# Changes

Every revision of the Context Window Architecture specification while it is a draft, newest first. [SPEC.md](SPEC.md) is the text they describe.

**Draft history.** The 2026-09-22 revision separated instruction authority from factual precedence; made freshness, producer exclusions, refusal traces, clock snapshots, token accounting, and draft evaluation status explicit; and published executable JSON contracts and shared validators. Example profiles are all unevaluated. Changelog entries older than that revision describe superseded draft behavior.

## 2026-10-07 · numbers however they are written

- Conformance corpus: three new cases and one changed. All four listed assemblers passed every published case, while generated inputs found a defect in three of them that no case reached. The conformance README already decides each, so no requirement changes. The README's Numbers section and its defaults_filled rule now name the cases.
- doubles-nearest writes scores near 2^53 with fractions and exponents, including halfway values that round to even, and doubles-largest writes the largest double as 1797693134862315700E290 and as 1.7976931348623158e308, which rounds to it rather than out of range. Each must be read as the nearest double, which a parser that is not correctly rounded misses.
- integer-written-as-double repeats diversity-cap with max_per_source written 2.0. That is the same double as 2, which JSON Schema also counts as an integer, so the case has diversity-cap's decisions and payload. generators/conflicts.py now reads the cap as an integer, so it builds this case too.
- admission-reasons: two candidates excluded with duplicate_item_id now leave lineage to the slot default, so defaults_filled lists them (R-3: it covers items later excluded). Its snapshot, trace and digest change; its payload does not.
- Implementations count the three new cases, and admission-reasons, as not run until they run them again. Fixes contextwindowarchitecture/contextwindowarchitecture#7; see contextwindowarchitecture/assembler-go#1, contextwindowarchitecture/assembler-python#1 and contextwindowarchitecture/assembler-rust#1.

## 2026-10-06 · digests of numbers beyond 2^53

- generators/digest.py wrote a whole double beyond 2^53 as its exact value, where RFC 8785 writes ECMAScript's shortest round-trip digits padded with zeros: 12345678901234567890 came out as 12345678901234567168 rather than 12345678901234567000. The conformance README's Snapshot digest already said the second, and the Python, TypeScript, Go and Rust assemblers already computed it; only the generator departed, and no published case held such a number, so every published digest is unchanged. It now writes such a double as ECMAScript does, and a test holds it to JavaScript's output.
- Conformance corpus: the new digest-beyond-2-53 case holds scores of more than 17 significant digits, as integers and as a fraction with an exponent, which round to the same double as min_relevance and pass, and one that rounds to the double below and is below_threshold. A digest that writes the exact value fails it. Implementations count it as not run until they run it. No requirement changes.
- Fixes contextwindowarchitecture/contextwindowarchitecture#3.
- Implementations: the Python, TypeScript, Go and Rust assemblers vendored this revision with no code change, each passing 62 cases, digest-beyond-2-53 included, and rejecting 25 rejections.

## 2026-10-04 · admission codes for any JSON type

- R-1: an item whose slot, or authority, is not in the closed set is excluded with unknown_slot, or unknown_authority, whatever its JSON type. A slot of 5, null or an array also fails the schema's type, so two codes applied, and R-21 already recorded the earlier one, but nothing said so and no case held such a value: a black-box run of the four implementations found three recording unknown_slot and unknown_authority and one recording invalid_structure, while all passed every case. The reason codes and the conformance README now say it, and nothing else behaves differently.
- Conformance corpus: admission-reasons adds five candidates, a slot that is a number, null or an array and an authority that is a number or null, each excluded with its unknown code, so its snapshot, trace and digest change. Its payload does not.

## 2026-10-04 · prompt caching

- Provider prompt caches reuse a request's leading part only up to the first byte that changed, and nothing here said how an assembled payload meets one. The entries below make the part of each call that the next one repeats exact and visible, and say what the application owns.
- R-7: prior turns in interaction.history render in the order they were said: by freshness, which for a turn records when it was said, compared as instants at full precision, and by id only among turns said at the same instant. Every item within a placement went by id, so a transcript's order rested on how a producer spelled its ids, and the published conflict-instruction case rendered turn:9 after turn:13. A new turn now lands after every earlier one, so the history's leading part repeats from one call to the next. The conformance README's trace order, its Ordering section and every renderer say the same; no other slot's order changes.
- Conformance corpus: conflict-instruction's turn:10 is now said at 11:47, before turn:11, so its rendered turns read in turn order, and its payload, trace and digest change. The new history-freshness-order case holds turns whose ids sort against the order they were said, a freshness written with an offset, and two turns said at the same instant with fractions of different lengths, which fall back to id order.
- cwa-message-blocks/v1, a renderer published as optional: the request cwa-messages/v1 renders, with the user message as one {id, text} entry per placed item, so an application can put a provider's cache breakpoint at any item boundary, and the boundary a breakpoint marked on one call still exists on the next. A surfaced member's entry names its group as a system entry does, and keeps its mark in the text. Its count sums every entry's text, so estimate-utf8/v1 can fit fewer items than under cwa-messages/v1, which the blocks-budget case holds. cwa-messages/v1 and its cases are unchanged. The conformance README lists the new renderer under a heading of its own, Optional; an implementation that leaves it out skips blocks-render, blocks-budget and the rejection blocks-system-after-xml, and still stops on an application renderer under its ID (R-16).
- Example profiles: cache-first-chat/v1 joins the other five, on the support-chat route and unevaluated, ordered for prompt caches. Governance, the user profile and memory open the payload, the history follows and grows at its end (R-7), and the evidence, observations, task state and query a turn refills close it, so one call repeats the last one's leading part through its last turn. The other five keep their order, which follows attention, and the Evidence page's explorer diffs any two. The registry pins it beside them.
- §1: request structure the renderer leaves to the application, such as a provider's cache breakpoints, cache lifetime or cache key, adds no text, so the count and hash a trace records still describe what the model reads. §1 required the handoff to add no text of its own and did not say whether cache markers count as text. No requirement changes, and nothing behaves differently.
- §5 now says placement also decides how much of one call's payload the next call repeats, and points to the Evidence page's new section on prompt caches, which sets out what the profile, the renderer and the application each own, with the providers' documented behaviour. §6.1 lists a cache-reuse test: two consecutive turns under a cache-ordered profile render the same leading bytes through the earlier call's last turn (R-7, R-23). No requirement changes, and nothing behaves differently.
- Implementations: the Python, TypeScript and Go assemblers vendored this revision and re-ran the corpus, 61 cases and 25 rejections each, with none skipped. Each renders history in the order turns were said and provides cwa-message-blocks/v1, and the Python assembler's status matrix is unchanged. The port template's scripts treat a component listed under Optional as optional, so a port that leaves it out skips its cases rather than failing them, and they decide a skip from the component the port says it lacks, so a port lacking a required component fails every case that uses it, even one that also uses the optional renderer.

## 2026-09-29 · who can claim conformance, and on what

- §1: a producer's conformance is an agreement about what it emits, and rests on its word. An assembler's rests on a conformance report showing that it passes every published case and rejects every published rejection for the tokenizers and renderers it provides. §1 never said what backs either claim, or whether an assembler that skips the cases for a renderer it lacks may claim conformance; it may, for the ones it provides.
- §1: a conformant application uses a conformant assembler and only conformant producers, and meets the MUSTs no component can meet for it (R-5, R-8, R-11, R-12, R-15, R-19, R-20, R-23). Its claim is an agreement too, except for its assembler's part, which that assembler's report backs. §1 named the application's duties only to say they weren't the assembler's, so nothing stopped a product calling itself conformant because its assembler was. These three are now the only claims the specification defines.
- §1: a conformant application also renders with a renderer the published cases cover, and hands the payload to the model with each text in the platform role its renderer assigns, text assigned none in the live user turn, and no text of its own. A renderer no case uses leaves R-7's roles untested, and an adapter that moves or adds text changes what the model receives after the trace has counted and hashed it. No requirement changes, and nothing behaves differently.

## 2026-09-27 · closed predicate, retrieval gate, code traceability

- A review from an implementer's side found three requirements that could not be met as written and eight reason codes that no requirement named. No rule contradicted another, and the README already settled every ordering. The changes below close the gaps; the conformance cases pin the two that change behaviour.
- R-13: a retrieval producer's candidates go in evidence.knowledge or evidence.tool_results, with the authority R-1 gives that slot. R-13 used to demand reference_only, which R-1 forbids in tool results. A producer of kind retrieval is now gated to the evidence slots, as memory and mcp producers are, whatever the route lists; anything else is excluded with producer_slot_not_allowed. This is new behaviour. admission-reasons gains a retrieval item admitted in tool results, one there with reference_only authority, and one sent to governance.examples.
- R-3: the slot-level eligibility rules, min_relevance, max_age_seconds, required_scope and source_prefix, are the complete eligibility predicate. R-3 used to say the route owns an executable predicate, with nowhere in the route policy to put one, so two assemblers could disagree and both claim R-23. Every other admission check still applies. A future version may add rules or an extension mechanism, as Future work says.
- R-2: the sentence about normalizing legacy names is gone. No legacy name was ever defined, and every schema is closed.
- R-12: an evidence item is omitted for budget when its row says over_budget, whether for the payload, its token_budget or its slot's max_tokens. The evidence-cap-omitted case pins it.
- R-15: the route capability policy is the producer the grant's policy_producer names, listed by the route with kind capability_policy; a governance.capabilities item from any other producer, or off the allow-list, is capability_not_allowed. R-15 never said what made a producer the capability policy, so one implementation accepted a grant naming a producer of another kind and another did not. The capability-policy-kind case pins it.
- R-2: every number in a snapshot is a double, read as JavaScript reads it before any comparison, so an integer beyond 2^53 rounds the same way in every language, as it already did in the digest. A language that keeps integers exact compared 9007199254740992 and 9007199254740993 as different where JavaScript ties them, and the two assemblers disagreed on a snapshot with one digest. The README's Numbers section and the threshold-beyond-2-53 case pin it.
- Wording only: R-1 names unknown_slot and unknown_authority, R-2 missing_field and invalid_structure, R-4 required_slot_missing, R-8 stale_state, R-9 expired and revoked, R-17 protected_content_over_budget and R-18 duplicate_variant_id, so every code in contract/reasons.json is named by the rule it cites. R-2 says plainly that an item is expired when expires is at or before assembly_time. R-10 says marked items render inside their slot's wrapper and never in a platform role, where it said "as reference material". R-16 no longer says a profile can lower a tier, since profiles carry none. R-24 runs after supersession, as the README always said.
- conformance/check.py checks the contract's own consistency: schemas, digests, hashes, rejections, reason-code traceability and the generated copies of the requirements.
- The five example profiles now have the route policies they name, each \<route>/illustrative/v1, published in examples/route-policies.json and pinned in the registry beside the profiles, so a valid snapshot can carry each profile. A profile naming a route policy the registry lacks is now a problem check.py reports, not a warning.

## 2026-09-25 · one field, one decision

- Two conflict checks left five questions about authority, trust and the injection marker that only the README, the cases or a careful reading could answer. The requirements now answer them, and each field decides one thing.
- R-1: untrusted used to be allowed in every slot outside governance and knowledge, beside a MUST that each slot carry its own role, with nothing saying which won. Now it is an explicit exception for tool results, memory and history. State never carries it, because the application writes state (R-8). Nor does the query: an untrusted query still rendered as the live user turn, where the model takes its orders, while the spec said it couldn't instruct. Both are now excluded with authority_not_allowed, which is new behaviour; no case carried either. admission-reasons gains rows for both, and for untrusted items admitted in the three slots that allow it.
- R-6: authority alone decides who may instruct: governing and user items, and nothing else. "Untrusted content" used to name the authority value, the marker and the trust field at once. An item's trust and injection_risk never add or remove that standing, so a marked history turn with user authority is a peer like any other. R-11 now defines an instruction group's peers, and says a group with one peer or none is decided by authority. Nothing behaves differently; the conflict-instruction case gains g-trust-blind to pin it.
- R-10: the query and user turns in history keep user authority although marked. Material a user pastes or attaches into a query or history body renders with that body, since the assembler can't split one without a model call, and gains no authority from it; the application should delimit it in a form it cannot imitate. R-10 used to say such material is "rendered as reference material", which only an item of its own can be. R-10 also names the checks it relies on, untrusted_content_unmarked in the five marked slots and untrusted_in_governance by trust and marker, where it used to say "untrusted content". Nothing behaves differently.
- R-11: in a fact group, a member is eligible exactly when its producer is listed and it carries the policy's scope keys, and freshness breaks a tie only among the leaders from the top-ranked producer. Trust, the marker and the route's verified flag are never read; a route that prefers a verified server lists it first. The old "unverified claim" meant an ineligible member all along. A group left with fewer than two admitted members is moot before either kind's rules apply. Nothing behaves differently; the conflict-fact case gains f-trust-blind to pin it.

- Most of these rules were already checked by the conformance cases; now the requirements state them. The one new behaviour is the producer-kind gates below.
- R-14 and R-15 now say how they are enforced: a producer of kind memory sends only interaction.memory items, and one of kind mcp only evidence items, whatever the route lists. Anything else is excluded with producer_slot_not_allowed, except that a tool specification an MCP adapter sends to governance.capabilities still gets capability_not_allowed. Before this, a verified MCP server that the route listed for governance.instructions could write instructions.
- R-2 names duplicate_item_id, out_of_scope and future_freshness with clock_skew_seconds. R-3 makes max_age_seconds and source_prefix part of the route's eligibility predicate. R-13 names below_threshold, R-15 producer_not_authenticated, and R-16 protected_tier_changed.
- R-9: expires and revoked_by exclude any item that carries them, not only memory. Producer rows reach the trace from every batch.
- R-11: a conflict group may name a producer exclusion, and group ids are unique. R-15: one batch per producer. R-20: a profile's route and route policy version match the snapshot's, its renderer can realize it, and an unplaced protected item refuses with protected_slot_unplaced.
- R-17 points to the Snapshot checks in conformance/README.md and rejects strings that aren't well-formed Unicode. R-21 makes that README normative wherever the requirements leave an ordering, tie-break or boundary open.
- R-22's provenance fields, R-11's group_id and winner, and the rows a refused trace keeps (R-17) are now MUST: the cases already compared them, so an assembler that met every MUST could still fail. Only admission-stage timings stay SHOULD. A refused trace also has compressed: [], and defaults_filled is always present, if empty.
- R-9: a producer row's reason must be an exclusion code from contract/reasons.json, and the batch schema now checks it. A row with reason superseded carries superseded_by, which must name a candidate in the same batch, just as R-13's duplicate_of does. Before, such a row couldn't satisfy the trace schema at all.
- R-11: budget pressure can still omit a surfaced member, and the ones that stay keep their conflict marker. A conflict_unresolved refusal records recovery.action: request_context when every group behind it asked for context. R-12 gives each evidence slot its own minimum and says which recovery action applies when. R-16 counts what the renderer emits as text; roles in a message request aren't text, so margin_percent covers them. R-23 adds the capability allow-list to the inputs that fix an assembly.
- A second conflict check found three gaps in the changes above, now closed. An item's eligibility can't be blank, because the trace now repeats it; a blank one is invalid_structure. R-16 refuses on protected content before anything is reduced, as the cases always did, rather than after item caps. R-17 also rejects a number outside the IEEE 754 double range, such as 1e400, which has no RFC 8785 serialization.
- Wording only: R-3 names the slot rules its predicate includes, R-18 identifies variants per rendered occurrence, and R-25 and R-26 put their exemptions in the rule itself.
- assembly_time_required is gone from contract/reasons.json. A snapshot without a valid assembly_time fails its schema and is rejected, so that refusal could never happen.

## 2026-09-24 · prose caught up with the requirements

- R-16 now says outright what the 09-23 entry below already said: items can't lower a tier in a slot that's protected by default, but can in a slot only the route raised.
- The eight evidence steps now show who owns what. Rerank and Package belong to the producer (R-13). Conflicts, supersession, deduplication and source caps get their own step. Attribute is gone, because the assembler never edits the output contract.

- Retrieved passages are now chunks, which is what most retrieval tooling calls them. ## 2026-09-23 · admission edge cases

- R-2: missing_field:\<name> names a field of the item itself. A variant missing one of its own fields is invalid_structure.
- R-2: context_item.schema.json requires expires and relevance only of an item that names the memory or knowledge slot. An item without a slot is missing_field:slot; before, a JSON Schema if over an absent slot passed, and R-21's alphabetical rule recorded missing_field:expires.
- R-8: a state item from a producer whose kind is not state is excluded with producer_slot_not_allowed, even when the route lists that producer for the slot.
- R-2: duplicate_item_id counts every other candidate, whatever its own outcome, and every producer exclusion, in any batch. Each candidate sharing an id takes the earliest code that applies to it.
- R-16: protected_tier_changed guards the slots protected by default. In a slot the route raised to protected, an item may still lower its own tier.
- R-9: producer exclusion rows reach the trace from every batch, including one whose producer the route does not admit. Rows that share an item_id, and candidates that share an id, order by their RFC 8785 bytes, as the snapshot digest does, so snapshots with the same digest give the same trace.

## 2026-09-23 · slot caps & floors, deduplication, supersession, source diversity

- A route may cap a slot's share of the payload with slots.\<slot>.max_tokens (R-16). The cap holds whether or not the payload fits, after token_budget caps and before budget pressure; protected items alone over it refuse with protected_content_over_budget.
- A route may hold a slot at a floor with slots.\<slot>.min_tokens (R-16). Budget pressure never makes a reduction that leaves the slot below it, and freezes the slot once one is withheld; the payload then either fits or is refused with slot_floor_over_budget (R-17). A floored slot may keep droppable items while other slots compress, the one exception to R-16's tier order.
- New R-24: a route may ask a slot for exact deduplication with slots.\<slot>.dedupe: exact. After conflict resolution, an item whose body equals a kept item's body once whitespace is collapsed is excluded with duplicate_content, and excluded[].duplicate_of names the item kept. Protected items and conflict-group members are never excluded.
- New R-25: a route may ask a slot to supersede stale observations with slots.\<slot>.supersede: source. After conflict resolution and before deduplication, an item is excluded as superseded when the same authenticated producer sent an item with the same source and a later freshness; items tied for the latest instant are all kept, excluded[].superseded_by names the item kept, and protected items and conflict-group members are never excluded.
- R-13: a retriever that drops a passage as a near-duplicate reports it in its batch's excluded list as duplicate_content, with duplicate_of naming the candidate it kept; the trace carries the row as reported.
- New R-26: a route may cap a slot at slots.\<slot>.max_per_source items per authenticated producer and source. After deduplication, the lowest-ranked items beyond the cap are excluded with source_diversity_cap; protected items and conflict-group members are never excluded and take places first.
- R-17 separates rejection from refusal. A snapshot that fails its schemas or the snapshot checks is rejected before assembly, with no payload and no trace; refusals are outcomes of valid snapshots. A producer id may head only one batch.
- R-16: budget.margin_percent (an integer from 0 to 100) reserves a safety margin for a tokenizer that estimates. Only the test of whether the whole payload fits scales the count by it; caps, floors and traced counts do not, and the trace's budget repeats it.
- Conformance defines estimate-utf8/v1, a portable tokenizer that counts UTF-8 bytes divided by 4, rounded up, for models with no local tokenizer. It is meant for use with budget.margin_percent.
- R-19 and R-21: a profile names the specification it was written for in spec (cwa/draft until the first release), a profile for another specification is rejected, and every trace repeats it in context.spec.
- Requirement IDs stay permanent: new requirements append after R-23 rather than renumbering a section.

## 2026-09-22 · conflict resolution

- R-11 defines what resolution does to the payload. Authority excludes nothing; among governing or user peers, one governs and the rest defer excludes the deferring peers (conflict_deferred). Fact policy excludes the other members (conflict_lost). No conflict excludes a protected item.
- Route policy gains facts.\<key> (precedence by authenticated producer, scope, freshness_tiebreak, on_unresolved) and on_unresolved_instruction. Surfaced members are marked in the payload.
- conflicts[].resolution becomes resolved, surfaced, context_requested, refused or moot; an optional winner names the member that prevailed.
